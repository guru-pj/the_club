# Database Migrations (Flyway)

Every service that owns a database manages its schema with [Flyway](https://documentation.red-gate.com/flyway).
Hibernate no longer creates or alters tables. It runs with `ddl-auto: validate`, so a service refuses to start
if its entities and its database disagree.

| Service | Database | Migrations |
|---|---|---|
| user-service | MySQL `userdb` | `user-service/src/main/resources/db/migration` |
| auth-service | MySQL `authdb` | `auth-service/src/main/resources/db/migration` |
| club-service | MySQL `clubdb` | `club-service/src/main/resources/db/migration` |
| event-service | MySQL `eventdb` | `event-service/src/main/resources/db/migration` |
| notification-service | MySQL `notificationdb` | `notification-service/src/main/resources/db/migration` |
| activity-service | PostgreSQL `activitydb` | `activity-service/src/main/resources/db/migration` |

## How it works

On startup, before JPA initialises, Flyway compares the scripts in `db/migration` with the
`flyway_schema_history` table in that service's database and applies any pending ones in version order, each in
its own transaction where the database allows it. Then Hibernate validates the entity mappings against the
resulting schema.

`V1__baseline.sql` in each service is the complete schema as of the Phase 1 + 2 release.

### Conventions

* **File names:** `V<version>__<description>.sql`, for example `V2__add_club_banner_url.sql`. Versions are
  integers, increasing per service. Pick the next free number; never reuse one.
* **Never edit a migration that has been applied anywhere** (dev databases included). Flyway checksums every
  applied script and fails startup when one changes. Fix mistakes with a new migration.
* **Enums are stored as `VARCHAR`**, not MySQL `ENUM` or PostgreSQL check constraints, so adding an enum value
  needs no migration. Removing or renaming a value does need one, to update existing rows.
* **No cross-service foreign keys.** IDs that belong to another service (user, club, event…) are plain
  `CHAR(36)` columns. Foreign keys exist only between tables of the same service.
* MySQL tables use `ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci`.
  UUIDs are `CHAR(36)`, timestamps `DATETIME(6)` (MySQL) or `TIMESTAMP(6)` (PostgreSQL), and money `DECIMAL(10,2)`.
* Write SQL that also runs on H2 in MySQL or PostgreSQL compatibility mode, because the unit and integration
  tests run on H2. Plain `CREATE TABLE`, `ALTER TABLE ... ADD COLUMN` and `CREATE INDEX` are fine. If a statement
  truly can't be portable, put the vendor-specific version under `db/migration/{vendor}` and add
  `{vendor}` to `spring.flyway.locations`. Avoid this if at all possible, so each migration has one source.

### Example: adding a column

1. Add the field to the entity:
   ```java
   @Column(name = "banner_url", length = 500)
   private String bannerUrl;
   ```
2. Add `club-service/src/main/resources/db/migration/V2__add_club_banner_url.sql`:
   ```sql
   ALTER TABLE clubs ADD COLUMN banner_url VARCHAR(500);
   ```
3. Run `mvn -f club-service/pom.xml verify`. Every test context applies the migrations and validates the
   entities, so a mismatch (wrong type, missing column) fails the build.

For a `NOT NULL` column on a table that already has rows, add it as nullable, backfill it, then add the
constraint, in the same migration or across several.

## Existing databases created by Hibernate

Databases created before Flyway (by `ddl-auto=update`) have tables but no `flyway_schema_history`. Each service
sets:

```yaml
spring:
  flyway:
    baseline-on-migrate: true
    baseline-version: 1
```

On the first start, Flyway records such a database as already at version 1 without running
`V1__baseline.sql`, then applies V2 onwards normally. A brand-new empty database runs V1 as usual.

This assumes the existing schema matches V1, which holds for any database created by the Phase 1 + 2
code. `ddl-auto: validate` still runs afterwards, so a drifted database is reported at startup instead of
silently corrupting data.

## Tests

* **Every Spring test context** (H2) runs Flyway and then `ddl-auto: validate`. Each context gets its own
  in-memory database (`jdbc:h2:mem:${random.uuid}`), so tests stay isolated.
* **`*MigrationIntegrationTest`** (one per service) boots the service against a real `mysql:8.4` or
  `postgres:15` container through Testcontainers. These tests run wherever Docker is available, for example in CI,
  and are skipped automatically otherwise.

## Verification performed for V1

The V1 scripts were checked against real database engines (no Docker), not just H2:

* **Engines:** MySQL Community Server 8.4.6 (official generic Linux tarball) and PostgreSQL 15.10 (zonky
  embedded binaries).
* **Reference DDL:** generated by Hibernate itself for each real dialect (JPA schema-generation script), and the
  V1 files were written to match it, with readable constraint names and VARCHAR enums.
* **Fresh database:** for each of the six services, Flyway applied V1, Hibernate `validate` passed and the
  application reached the started state. A second start reported "Schema is up to date. No migration
  necessary".
* **Baseline path:** for each service, a database was first created by the old `ddl-auto=update`. Starting
  with Flyway + validate then baselined it at version 1 and validation passed.
* **Runtime:** the whole stack (all services plus the gateway) ran on Flyway-managed MySQL/PostgreSQL databases
  and `scripts/smoke-test.sh` passed end to end. That run exercised the intra-service foreign keys during
  registrations, payments, check-ins and posts.
